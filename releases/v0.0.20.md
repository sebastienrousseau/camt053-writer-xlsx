# camt053-writer-xlsx v0.0.20

No writer changes: `write_xlsx` behaves exactly as it did in 0.0.16.
What this release adds is a benchmark that measures the thing most
likely to kill an export job, and the suite tooling this repository was
missing.

## Why the number jumped from 0.0.16

The `camt053` suite ships **one version number across all six packages**
by policy, and it had drifted to six different ones — 0.0.18, 0.0.18,
0.0.19, 0.0.18, 0.0.16 and 0.0.16. Nothing breaks when that happens,
which is exactly the problem: a member left a release behind still
installs and still passes its own tests. Only the index disagrees.

All six now sit on **0.0.20**.

## The benchmark measures memory, not just time

Writing xlsx means building the **entire workbook in memory** before
anything reaches disk. Time is the less interesting half; the number that
decides whether a job survives is peak memory.

| entries | ms | peak MB | file MB | peak/file |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 20.2 | 0.82 | 0.015 | 56× |
| 1,000 | 155.2 | 5.09 | 0.079 | 65× |
| 5,000 | 674.2 | 27.67 | 0.357 | **78×** |

xlsx is zipped XML and compresses hard, so **the output file is a bad
proxy for what the process needs**. A 0.36 MB workbook costs around
28 MB of peak heap. An export sized from the file it produces will be
killed in a container that looks generously provisioned, long before the
disk notices anything.

Size the process from the row count instead.

Two deliberate points of honesty in the output:

- The growth verdict does not flatter small samples. An exponent below
  1.0 does not mean sublinear work — it means the fixed per-workbook
  cost has not amortised yet — and the benchmark says so rather than
  printing "linear". Across 100 → 5,000 entries, time and peak both
  measure 0.90.
- Peak comes from `tracemalloc`, which sees Python-level allocations
  only. Whatever the zip encoder allocates in C is not counted, so the
  printed figure is a **floor**, not a budget.

## A scheduled drift check

`scripts/check_suite_consistency.py` runs daily and compares this tree,
and every published member, against PyPI, exiting non-zero when they
disagree.
